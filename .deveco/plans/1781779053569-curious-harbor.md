## Design

### S1: 修复安全关键 stub

#### S1.1: RuleEngineStub → 真实 RuleEngine

**文件**: `hsp-service/src/main/ets/service/RuleEngineStub.ets`

**方案**: 重写为 `RuleEngine.ets`，实现 `IRuleCalculator.calculate()`：

```
输入: IRuleEngineParams (family, healthSignal, foodLabel, dailyBudget)
输出: Recommendation (level, levelColor, reasons[], maxServings)

算法:
1. 遍历 family.members，对每个成员:
   a. 检查健康目标 vs 食品营养：
      - 控压 + 高钠(≥500mg/100g) → CAUTION, reason="高钠食品不适合控压人群"
      - 控糖 + 高糖(≥15g/100g) → CAUTION, reason="含糖量偏高，控糖人群注意"
      - 控脂 + 高脂(≥17.5g/100g) → CAUTION
      - 减脂 + 高卡(≥500kcal/100g) → CAUTION
   b. 检查过敏原 vs 成员过敏档案 → AVOID + 过敏原名
   c. 检查不耐受 vs 成员不耐受档案 → CAUTION
2. 检查每日预算消耗:
   a. 钠预算剩余 < 食品钠含量 → CAUTION + "今日钠预算将超标"
   b. 糖/卡/脂同理
3. 综合: 取最严格级别 (AVOID > CAUTION > SUITABLE)
4. maxServings: 基于预算剩余 / 单份营养量计算
```

导出名从 `RuleEngineStub` 改为 `RuleEngine`，更新 hsp-service Index.ets 导出和所有引用点。

#### S1.2: SecureStorageUtil crypto 修复

**文件**: `hsp_core/src/main/ets/utils/SecureStorageUtil.ets`

**方案**:
- `FIXED_TAG_PLACEHOLDER` → 使用加密时生成的真实 GCM tag，存储到偏好设置 key `crypto_gcm_tag`
- `FIXED_IV` → 每次加密生成随机 IV (12 bytes)，与密文一起存储
- 解密时从存储中读取 IV 和 tag，验证完整性

#### S1.3: SecureHttpClient cert pin 修复

**文件**: `hsp-service/src/main/ets/service/SecureHttpClient.ets`

**方案**:
- 当前 4 个 FILL_ 占位 → 改为开发阶段 `CERT_PIN_MODE=REPORT_ONLY`（日志警告但不阻断）
- 提取真实 cert fingerprint 需要后端部署后从证书提取，本次先确保不阻断 HTTPS 请求
- 添加 `canIUse` 检测和运行时降级

### S2-S3: 实现替代品推荐服务层桥接

**问题**: `AlternativeRecommenderStub` 在 hsp-service 返回空数组，而真正的 `AlternativeFoodRecommender` (701行) 在 feature-scan 中，hsp-service 不能依赖 feature-scan。

**方案**: 在 hsp-service 新增 `AlternativeRecommenderService.ets`，通过依赖反转接口调用：

1. 在 hsp_core 新增 `IAlternativeRecommender` 接口：
```typescript
export interface IAlternativeRecommender {
  recommend(foodId: string, count: number): Promise<EnhancedFoodRecommendation[]>;
  recommendAlternatives(foodName: string, category: string, count: number): Promise<AlternativeFood[]>;
}
```

2. feature-scan 实现该接口，包装 `AlternativeFoodRecommender`

3. hsp-service 的 `AlternativeRecommenderStub` → `AlternativeRecommenderAdapter`，持有 `IAlternativeRecommender | null`，运行时注入

4. ServiceManager 在 entry 初始化时注入真实实现

### S4: 修复 BalancePage 硬编码营养数据

**文件**: `entry/src/main/ets/pages/BalancePage.ets:372-516`

**方案**: 将 21 个场景的硬编码 Map 改为从 `MealScenarioNutrition` 数据源查询：

1. 在 hsp_core 新增 `MealScenarioNutrition.ets`，包含 21 个场景的**差异化**营养数据（每场景独立 carbs/protein/fiber 值）
2. 数据来源：参考《中国食物成分表》标准值，按典型份量（非 100g，而是实际食用量）计算
3. BalancePage 从该数据源读取，而非硬编码

关键改进：每个场景的 carbs 和 protein 必须差异化（奶茶 ≠ 烧烤 的蛋白含量）

### S5: 实现 OnDeviceInferenceEngine 真实推理

**文件**: `feature-scan/src/main/ets/engine/OnDeviceInferenceEngine.ets`

**当前**: 本地 `namespace mindSporeLite` stub，`loadModelFromBuffer`/`createSession` 返回 null

**方案**: 
1. 删除本地 `namespace mindSporeLite` stub
2. 改为 `import { mindSporeLite } from '@kit.MindSporeLiteKit'` + `canIUse` 检测
3. 复用 hsp-llm 的 `ModelManager.loadModelWithMindSpore()` 和 `OnDeviceLlmBridge` 推理链路
4. 保持现有 heuristic fallback 作为降级（confidence 标记为低）
5. `predictNutriScore()` 优先使用 MindSpore Lite 模型，fallback 到加权公式
6. `predictIngredientRisk()` 优先使用模型，fallback 到关键词匹配

### S6: 清理 OnDeviceAiEngine 假推理

**文件**: `feature-scan/src/main/ets/engine/OnDeviceAiEngine.ets`

**当前**: `runInference()` 返回硬编码 JSON（E250, E951），`loadModel()` 永远返回 false

**方案**:
1. `runInference()` → 接入真实 `IngredientSemanticEngine` + `AdditiveSafetyEngine` 的组合分析
2. `loadModel()` → 使用 `canIUse('SystemCapability.AI.MindSporeLite')` 检测 + `ModelManager`

4. `OnDeviceAiService.runLocalInference()` → 删除 setTimeout 假延迟，改为调用 `IngredientDeepAnalyzer`
